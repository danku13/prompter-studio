# Планы внедрения Prompter Studio

Этот раздел содержит архитектурные планы развития Prompter Studio — веб-редактора
сценария с мобильным суфлёром. Документы описывают **что и как внедряем**:
модели данных, потоки, точки интеграции, этапы и чек-листы. Код пишется по этим
планам отдельными итерациями.

Планы согласованы с фактической архитектурой репозитория (Next.js 16 App Router,
TypeScript, Prisma/SQLite, shadcn/ui, socket.io-мини-сервис на порту 3030,
Capacitor-APK для Android) и с результатами локального аудита безопасности
(детали аудита не публикуются; см. внутренний документ `docs/security-audit.md` —
в git он не попадает). Пункты роадмапа аудита, которые закрывают эти планы:
REST-аутентификация (PIN → сессии), безопасное хранение секретов и
токенов, минимизация собираемых данных.

## Этапы (майлстоуны)

| Этап | Состав | Предусловия | Что даёт пользователю |
|---|---|---|---|
| **M1 — Онбординг + Help** | Интерактивный курс (7 шагов), Help-центр с повторным запуском курса, фиксация «прошёл/не прошёл» в localStorage | PIN-фикс (P0, отдельная задача) | Новый пользователь за 5–10 минут понимает: сценарии → импорт → AI → телефон → суфлёр/запись |
| **M2 — Регистрация + опрос** | NextAuth (Яндекс ID + Google ID), модели User/Account/Session/OnboardingProfile/SurveyResponse, миграция онбординг-статуса в профиль, опрос при регистрации, сессия ИЛИ PIN для `/api/*` | M1 (курс уже существует, мигрируем его статус), PIN-фикс | Устойчивая идентичность между браузерами/машинами; данные о канале привлечения |
| **M3 — Платежи** | Тарифы Free/Pro, интерфейс `PaymentProvider`, адаптеры ЮKassa и Prodamus, вебхуки, подписки, чеки 54-ФЗ | M2 (платежи привязаны к User), публичный HTTPS-домен | Разовая покупка Pro и подписка месяц/год |

Порядок внедрения **строго последовательный для M2→M3** (платежи невозможны без
аккаунтов) и **параллельный для M1** (онбординг не зависит от авторизации;
см. ниже).

## Ключевые архитектурные принципы (сквозные)

1. **LAN-режим всегда работает без интернета.** Регистрация и платежи —
   опциональные надстройки: сервер на компьютере пользователя продолжает
   полноценно работать локально (PIN-защита, QR-pairing, WS-синхронизация).
   Облачные функции деградируют изящно (graceful degradation), а не ломают
   локальные.
2. **Принцип одного писателя не меняется.** Все правки сценария идут через
   штатный автосейв → ревизия → broadcast в суфлёр. Ни одна новая фича
   (онбординг, AI, платежи) не пишет в сценарий в обход этого пути.
3. **Секреты — только на сервере.** Токены провайдеров (OAuth, платежные)
   хранятся в БД на сервере, шифруются at-rest, наружу отдаются масками.
   В localStorage/AS-хранилище телефона секретов нет (см. планы 02 и 04).
4. **Минимизация данных.** Запрашиваем минимальные OAuth-scopes; опрос —
   опциональный; содержимое сценариев в облако не копируется без явного
   функционала (планы 02/03).
5. **REST-контракт расширяется, не ломается.** Новые поля добавляются с
   обратной совместимостью (nullable `ownerUserId` у Script и т.п.); контракт
   документируется в `src/lib/types.ts`, как сейчас.

- Факты об API внешних провайдеров, подтверждённые поиском по официальной

## Как вносить изменения в планы

- План обновляется до начала реализации задачи; устаревшие решения фиксируются
  в разделе «Открытые вопросы» с датой.
- Коммиты с реализацией ссылаются на номер плана (`docs/plan/NN-*.md`).
- Изменение объёма (новые шаги/модели) — правка плана в том же PR, что и код.

## Критерии готовности этапов (DoD)

**M1:** E2E — первый визит → 7 шагов → завершение/пропуск; курс перезапускается
из Help; «Позже» возвращается при следующем визите; keyboard-доступность
проверена табом; мобильная ширина 390px без поломок; lint 0.

**M2:** вход через Яндекс ID и Google ID на свежем инстансе; LAN-режим без
интернета продолжает полноценно работать (PIN + pairing); REST принимает
«сессия ИЛИ PIN»; в БД `Account` — только шифротекст токенов; локальные
сценарии привязываются к аккаунту одной кнопкой; опрос проходит поток
«после онбординга»; выход и повторный вход стабильны; политика ПДн опубликована.

**M3:** тестовая покупка в demo-режиме Prodamus и на тестовом магазине ЮKassa;
вебхук с неверной подписью/IP отклоняется; повторная доставка вебхука не
выдаёт Pro дважды; сумма из тела вебхука сверяется с объектом у провайдера;
отмена подписки + dunning + grace работают; чек 54-ФЗ приходит на e-mail
покупателя; оферта и политика возврата опубликованы.

## Глоссарий

| Термин | Значение |
|---|---|
| LAN-режим | Сервер запущен на компьютере пользователя; телефон — в той же Wi-Fi; интернет не обязателен |
| Pairing | Подключение телефона по QR: короткоживущий токен сценария (текущая «сессия» суфлёра) |
| PIN-режим | P0-защита REST: bearer-токен после ввода PIN (для кафе/коворкингов) |
| BYOK | Bring Your Own Key: пользовательские ключи OpenAI/Claude для AI-функций |
| WS-мини-сервис | socket.io-сервис на порту 3030: real-time пуш сценария в суфлёр |
| Пролонгация (próroga/grace) | Период после неудачного списания, когда Pro ещё активен |
| Dunning | Цепочка повторных попыток списания при неудаче |
| Database session | Сессия NextAuth, хранимая в БД (`Session`), cookie — только указатель |
| Связка (binding) | Prodamus: сохранённая карта (`binding_id`) для списаний через `/rest/payment/do/` |
| Смарт-платёж | Сценарий ЮKassa, когда выбор способа оплаты происходит на их стороне |

## Что из планов проверено внешними источниками

Сводка (детали — в соответствующих планах; дата проверки: 2026-09-04):

- **Яндекс OAuth 2.0** — endpoints авторизации/токена/userinfo, форматы,
  scope-модель, поддержка PKCE (план 02).
- **Google OAuth 2.0 / OIDC** — endpoints, scope, бренд-требования к кнопке
  (план 02).
- **ЮKassa API v3** — создание платежа, аутентификация, идемпотентность,
  события вебхуков и их IP-диапазоны, модель рекуррентных платежей
  (`save_payment_method` / `payment_method_id`) (план 04).
- **Prodamus payform** — единый endpoint `do=link|pay`, алгоритм
  HMAC-SHA256-подписи, формат вебхуков (`payment_status`, `payment_init`),
  рекуррентные сценарии (клубная система, связки), demo-режим (план 04).

«⚠️ уточнить при внедрении» помечены: точные комиссии/тарифы, наличие
тестового стенда ЮKassa, имя Sign-заголовка Prodamus, детали бренд-китов
кнопок входа, отдельные REST-методы управления подписками.
