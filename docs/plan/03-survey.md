# План 03 — Опрос при регистрации

Статус: 📋 план (M2, зависимость — план 02: нужен `User` и сессия).

Требование пользователя: «при регистрации нужно проводить опрос откуда
пользователь узнал про сервис и для чего он конкретно будет использовать его».

---

## 1. UX

### 1.1. Когда показываем

Модальный диалог **после первого входа** — не в момент OAuth (окно
провайдера и так перегружено; после редиректа пользователь возвращается
в продукт и отвечает спокойно). Строгий порядок:

```
регистрация (OAuth) → онбординг-курс (план 01) → опрос
```

Опрос не показывается, пока курс не завершён/пропущен (не более одного
«прерывания» за раз). Повторно — по правилам §1.3.

### 1.2. Поведение

| Ситуация | Поведение |
|---|---|
| Первый вход, курс завершён | Автопоказ модалки через ~1 сек после закрытия курса (один раз) |
| «Пропустить» | Закрывается; **ненавязчивая точка** в меню профиля («Ответить на 2 вопроса») остаётся до заполнения |
| Закрытие по Esc / клик мимо | = «Пропустить» (не считаем заполненным; точка в меню остаётся) |
| Уже отвечал | В настройках профиля — раздел «Опрос» с текущими ответами, можно изменить (upsert той же записи) |
| LAN-режим без аккаунта | Опрос недоступен (персональных данных нет — опрос привязан к `userId`) |

Точка в меню — маленький индикатор (primary-цвет, 6px) у пункта «Опрос»;
исчезает после заполнения. Никаких модалок-«загонял»: больше одного
автопоказа за всё время.

### 1.3. Условия автопоказа

- `SurveyResponse` для userId отсутствует **и** онбординг завершён/пропущен
  (по `OnboardingProfile`) **и** пользователь ещё не «Пропускал» в этой
  сессии (флаг на сессию, не персистится).
- Один автопоказ на аккаунт. Дальше — только вручную из меню профиля.

## 2. Вопросы и варианты (ru)

Требование: 2 вопроса + опциональный открытый (в базовой версии —
2 обязательных выбора + 1 опциональный частотный + 1 опциональное поле
«другое»/заметки).

### Q1. «Откуда вы узнали о Prompter Studio?» (single choice, обязателен)

| Ключ (enum-строка) | Вариант ответа |
|---|---|
| `search` | Поиск (Google / Яндекс) |
| `friends` | Рекомендация знакомых |
| `youtube` | YouTube / обзор |
| `social` | Соцсети (Telegram, VK и др.) |
| `ads` | Реклама |
| `article` | Статья / блог |
| `other` | Другое (свой вариант — текстовое поле при выборе) |

### Q2. «Для чего будете использовать?» (single choice, обязателен)

| Ключ | Вариант |
|---|---|
| `youtube_long` | YouTube / длинные видео |
| `shorts` | Reels / Shorts / TikTok |
| `courses` | Онлайн-курсы и вебинары |
| `podcasts` | Подкасты |
| `corporate` | Корпоративные видео |
| `streams` | Стримы |
| `other` | Другое (свой вариант) |

### Q3. «Как часто снимаете видео?» (single choice, опционально)

| Ключ | Вариант |
|---|---|
| `rarely` | Редко (реже раза в месяц) |
| `weekly` | Почти каждую неделю |
| `daily` | Почти каждый день |

### Q4. Открытый (опционально)

«Что бы вы хотели видеть в сервисе в первую очередь?» — свободный текст
(`notes`, ≤ 500 символов). Помечен как необязательный, placeholder
с примером.

Правила:
- Ключи `source`/`purpose`/`frequency` — enum-строки из списка выше
  (хранение — строки в SQLite, валидация — zod-enum в `src/lib/types.ts`).
- «Другое» без текста не сохраняем как `other`-пустышку: текст обязателен
  при выборе `other` (валидация на форме).
- Радиокнопки (shadcn RadioGroup) — один экран на десктопе; на мобиле —
  вертикальный стек с прокруткой; Enter = «Далее».
- Кнопки: «Далее» (шаг 2), «Отправить» (шаг 3), «Пропустить» — в шапке,
  серым.

## 3. Модель данных

Уже добавляется в `prisma/schema.prisma` параллельной задачей (контракт):

```prisma
model SurveyResponse {
  id        String   @id @default(cuid())
  userId    String   @unique
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  source    String   // enum-строка Q1: search | friends | youtube | social | ads | article | other
  purpose   String   // enum-строка Q2: youtube_long | shorts | courses | podcasts | corporate | streams | other
  frequency String?  // enum-строка Q3: rarely | weekly | daily
  notes     String?  // Q4, <= 500 символов
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

- `userId @unique` — одна запись на пользователя: повторное заполнение =
  **обновление** (upsert), история изменений не хранится (минимизация);
  `updatedAt` фиксирует последнее изменение.
- `sourceOther`/`purposeOther` — текст «своего варианта» сохраняем в
  `notes` с префиксом (`[source=other] …`), отдельные поля не заводим
  (минимизация колонок; при агрегации префикс парсится).

## 4. API

| Роут | Метод | Тело | Ответ |
|---|---|---|---|
| `/api/survey` | GET | — | `{ answered, survey?: SurveyResponse }` (только владелец сессии) |
| `/api/survey` | PUT | `{ source, purpose, frequency?, notes? }` | `{ survey }` (upsert, zod-валидация enum-строк + длины) |

Авторизация: только сессия (cookie, план 02 §7) — без PIN (облачная фича).
Ответы видит только владелец аккаунта (GET отдаёт исключительно свою запись
— проверка `userId` из сессии в каждом хендлере).

## 5. Аналитика и приватность

### 5.1. Псевдоанонимная агрегация

- Владелец сервиса (админ) видит **только агрегаты**: количество ответов
  по каждому варианту Q1/Q2/Q3, разбивка по месяцам регистрации. Прямой
  выгрузки «userId → ответы» нет.
- CSV-экспорт в админке (раздел «Аналитика»): строки вида
  `месяц, source, purpose, frequency, count` — идентификаторы
  пользователей не выгружаются. При попытке доклеить join с users в UI —
  отдельно предупреждение, что это нарушает политику (тех.ограничение:
  экспорт-роут не умеет join, код отдельно не заводим).

### 5.2. Retention

- Ответы хранятся, пока активен аккаунт; при удалении аккаунта —
  каскадное удаление (onDelete: Cascade).
- Агрегированные счётчики (без привязки к лицу) могут храниться дольше —
  они не персональные (считаем на лету из ответов; отдельную таблицу
  агрегатов не создаём, пока объём < 10⁵ записей).
- «Пропустил опрос» — не хранится как персональная метка; только
  отсутствие записи (точка в меню — клиентская логика).

### 5.3. Согласие

Под опросом — одна строка: «Ответы используются только для развития
сервиса; увидеть и изменить их можно в настройках профиля» + ссылка на
политику ПДн (план 02 §6.6). Отправка ответов = согласие (лог с датой не
ведём отдельно — факт `createdAt` в записи).

## 6. План A/B и метрика

- **Гипотеза A:** опрос сразу после онбординга конвертит лучше, чем
  «точка в меню» (больше ответов, лучше качество канала привлечения).
- **Гипотеза B:** вынос Q3/Q4 на отдельный шаг после отправки Q1/Q2
  повышает completion (шаг 1 короткий — мотивация отправить основное).
- Раскатка: флаг `SURVEY_FLOW=v1|v2` (env, без БД-конфликтов), где
  `v1` = всё в одной модалке (базовая), `v2` = два шага (Q1/Q2 → Q3/Q4).
  Метрики: показ→отправка, показ→пропуск, доля заполненных через меню.
- Решение о победителе — по конверсии через 2 недели наблюдений
  (агрегат из §5.1).
